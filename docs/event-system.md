# 100マス版イベントシステム設計

状態: Phase 1基盤実装。ブラウザUIには未接続。完成200イベントカタログではない。

## 基本単位

- 1〜20: 最深部、21〜40: 廃棄物処理区画、41〜60: 生産・整備区画、61〜80: 管理・保守区画、81〜100: 地上接続区画。
- `expansionZoneForTile()` が1〜100を20マスずつに割り当てる。範囲外は例外。
- 各区画は最終的に40イベントを持つ。各プレイでは最大20件だけ選び、同一イベントIDを再使用しない。IDが尽きたときの重複補填は禁止。
- 旧15マス版は `src/game.ts` と `src/events.ts` に残り、`src/main.ts` が引き続き利用する。拡張エンジンのAPIは `src/expansion-engine.ts`。
- `EXPANSION_SAMPLE_EVENTS` は連携検証用の6件であり、完成イベント数に含めない。Phase 2では `docs/event-catalog.json` に設計概要200件を記録したが、本文・成功率・結果電力が未完成なのでランタイムカタログへ読み込まない。実際の100マス進行にはPhase 3以降で実装したイベントが各区画40件必要。
- Phase 2 JSON内の item / facility / NPC IDは設計上の参照名である。ランタイムへ移す段階で `ItemId`、`FacilityId`、`NpcId`、`ITEMS`、`FACILITIES`、`NPCS`、初期設備/NPC状態、実行時参照検査を同時に拡張し、その後にイベントデータを型検査する。P3-02で `coolant-diverted`、`ventilation-shutter`、`kabo`、`pico` を登録した。

## 候補抽選とイベント保証

イベントを選ぶ各マスで、次の順に処理する。

1. 次のタイルから区画を決める。
2. その区画の未使用イベントを集める。
3. `guarantee.when` が成立する未使用の保証イベントを優先度降順、ID昇順で1件選ぶ。保証イベントは通常抽選候補から常に除くため、先にランダム当選して予約を消費することはない。複数の保証イベントは優先度で順番に処理する。
4. 保証対象がなければ、未使用かつ `availableWhen` が成立する通常候補からseed付き乱数で抽選する。
5. 候補が0件なら、区画・タイルを含む明確な例外を出す。再抽選や重複で隠さない。

保証条件が成立したイベントの `availableWhen` も成立しない場合は、データ矛盾として例外にする。複数保証を同時に成立させる設計では、先行イベントによって後続条件が消えないことを依存テストで検証する。各区画の保証イベント数が20を超えるカタログは検証で拒否する。保証は同じIDを再抽選せず、成立した最初の適格タイルで優先する。

`validateEventCatalog()` はランタイムイベントID重複、3選択肢、成功率範囲、関連イベントID、区画の候補数（呼び出し側の `minimumPerZone` 設定）、保証枠の超過を検査する。Phase 2設計台帳はランタイム型を流用せず、`npm run validate:phase2` が件数、ID/資源参照、状態起点、前向き依存、循環、NPC状態、所持品利用順、予約上限を別途検査する。

## 状態と型

`ExpansionGameState` は位置、電力、使用済みイベントID、所持品、設備フラグ、NPC状態、選択履歴、アイテム履歴を保持する。`ItemId`、`FacilityId`、`NpcId` はIDのunion型で、選択肢効果と条件式から未知のIDをTypeScriptが拒否する。NPC状態は `unmet`、`encountered`、`rescued`、`rescue-failed`、`repaid`。

各データイベントにはID、題名、説明、区画、出現条件、保証条件、3選択肢、基本成功率、条件付き成功率、結果別電力差分/文章、アイテム、設備、NPC、後続関連、任意画像パスを定義できる。状態変化は成功または失敗の `OutcomeDefinition` に記述し、IDごとの大量分岐をゲーム進行コードへ追加しない。

### Phase 3 データの置き方と状態寿命

- 区画1/2本文はそれぞれ `src/expansion-content/zone1.ts` の `ZONE1_EVENTS`、`src/expansion-content/zone2.ts` の `ZONE2_EVENTS` に置く。各イベントの設計ID・名前・行動方向は `docs/event-catalog.json` と一致させ、後続リンクは `followUpEventIds` に記録する。各区画40件のうち30件は無条件の通常候補、10件は連携イベント。
- 出現理由は `availableWhen.explanation` で保持する。無条件イベントは `all: []` とし、場面固有の手掛かりを説明する。後続の条件付きイベントは `availableWhen` と `guarantee.when` に同じ状態条件を使う。
- Phase 2 `requires` の配列項目は全て満たすAND条件として `Predicate.all` に変換する。OR条件は別フィールドが定義された場合だけ表現し、未対応条件を省略しない。P3-02 zone 2の条件は単一条件で、`requiresAny` はない。
- アイテムは所持品に残り、設備フラグとNPC状態はゲーム状態に保持される。情報タグは履歴の `historyTags` に記録され、後続の `history-tag` 条件から履歴全体を参照する。これらに期限切れ処理はない。
- 状態効果はイベント結果の確定時にだけ適用される。ゲームエンジンがIDの重複出現を止めるため、同一イベントの効果は一度だけ適用する。失敗側と見送り側に成功状態を含めない。
- NPC初登場は `rescued` / `rescue-failed` / `encountered` を区別する。後続の再会条件は `rescued` だけを要求し、救出失敗と見送りは通常候補へ進む。
- 新しい状態IDを加えるときはunion型、表示名辞書、初期状態、参照検証、本文データ、テストを一緒に更新する。全区画を偽装したfixtureで本番カタログ件数を満たさず、必要な条件 fixture は `tests/` に明記する。
- `phase3Status` は `未制作`、`作業中`、`本文完成`、`要確認` を使う。構造検証だけでは文章を `本文完成` にせず、人の最終レビュー待ちは `要確認` とする。`runtimeReady=false` は200件と統合の完了まで維持する。

`illustration` は任意。未作成イベント画像を参照しないデータは正常に動き、Phase 5では画像欠落を表示フォールバックで扱う。画像未制作を完成扱いしない。

## 確率と結果の適用順

1. `successChanceFor(state, action)` が条件ルールの先頭一致を返す。ない場合は基本成功率を返す。
2. `toExpansionGameView()` はこの関数の `percent` と `reason` を表示し、スロット判定も同じ `percent` を使う。条件順が重なる場合はデータ定義順が優先。
3. `rollValue < percent` を成功とする。0%は必ず失敗し、100%は00〜99すべて成功する。
4. 選択したアクションのアイテム使用を記録する。消費時期は `attempt` / `success` / `failure` / `never` で定義でき、省略時は消費型が選択時、再利用型が非消費。未所持時は通常率・通常経路で選択を続ける。
5. 成功/失敗側の電力・所持品・設備・NPC・履歴タグを一度だけ適用し、結果を履歴へ確定する。電力は0〜20に制限。0ならGAME OVER、タイル100で電力が残ればCLEAR。
6. 終端でなければ次イベントを予約するが `position` と現在イベントは変えない。UIは結果全文後の続行操作で `continueExpansionAfterResult()` を呼ぶ。

電力0時とタイル100時は次イベントを抽選しない。アイテム所持数の既定上限は3、設定で変更可能。満杯時の入手は状態を変えず `capacity-full` 履歴と説明を残す。

## 因果表示

`ExpansionGameView` は出現理由、選択肢ごとの成功率と理由、結果、効果説明、所持品、設備/NPC状態、取得/使用/消費履歴を提供する。Phase 5 UIでは、出現したとき、選択前、結果確定後、NPC再登場時に次を見せる。

- 出現/再会理由（例: 以前、予備電源を復旧したため昇降機が使える）。
- 選択前の条件付き成功率と変化理由。
- 結果後の取得・消費・状態更新。
- 結果後に位置が変わらず続行待ちになる既存仕様。

条件ルールにプレイヤー向けの `reason`/`explanation` を含め、根拠不明の隠し補正を作らない。

## 実装上の境界と次段階

この段階ではランタイムのデータ型とサンプルに旧10イベントの移行は含まれない。NPC/item/facility辞書を追加した場合はunion型、表示名、状態検証、依存台帳、テストを同時更新する。任意画像パスの存在確認とフォールバック、画面表示、HUD記録、100マスの電力測定はPhase 5。
