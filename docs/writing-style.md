# Exit Sequence 文章スタイルガイド

## 1. 目的

本書をゲーム内文章作成の正本とする。ログを、主人公がその場で体験している文章へ統一する。静かな、シリアス寄りのSFを基本とし、判断に必要なゲーム情報は簡潔で明確に残す。ゲーム仕様・暫定値は [game-design.md](game-design.md) と [prototype-spec.md](prototype-spec.md)、表示と操作は [ui-layout.md](ui-layout.md) に従う。

## 2. 視点

日本語の一人称は「私」、英語は I / my とする。主人公が直接見た・聞いた・感じた情報、表示やAIから得た情報だけを書く。日本語では自然に主語を省略する。一人称視点と「私は」の反復を混同しない。

## 3. 日本語文体

常体、短文、冷静で観察的な語りを基本とする。現在形・現在進行の感覚を保つ。「通路を進む」「警告灯が点滅している」のように、その場の体験として書く。結果の余韻として自然な過去形は使えるが、過去の日記のようにしない。

## 4. 英語文体

First-person perspective, restrained and observational. Use short, natural sentences and primarily present tense. Keep atmosphere concise; avoid purple prose. Use I where English needs a subject, without starting every sentence with I. Translate meaning and game information rather than Japanese word order.

## 5. 主人公の地の文

感情を直接説明しすぎず、音、光、静けさ、呼吸、スーツの作動音、無人の設備、月面、非常灯、通信の沈黙などで雰囲気を伝える。観察から判断・行動へつなげる。性格を強く固定せず、性別・年齢・職業・過去を補完しない。

例：

```text
端末の表示を読む。
発進管制の安全ロックはまだ生きている。
ここから解除できそうだ。
```

## 6. AIの発言

日本語は必ず `AI：`、英語は必ず `AI:` で始める。簡潔・事務的・冷静に、必要な情報を優先する。主人公の地の文と混ぜない。AIに小説的な比喩を語らせない。軽い冗談も全体の静かなトーンを損なう場合は使わない。

## 7. システム情報

ENERGY増減・残量、成功率、脱出物資の所持、不足物資、READY / NOT READYなどは明示する。描写から数値や達成状態を推測させない。地の文とシステム情報は別の行、または明確な改行で区切る。AIが知らせる世界情報と、主人公が現場で知覚する情報を区別する。

## 8. 小説調にする文章

区画説明、移動・調査・設備観察、アイテム発見と回収、設備操作、通路の体験、遭遇、緊急退避、発進、終了前後の情景、実行確認前の説明、主人公が認識する前提不足を対象とする。

## 9. 小説調にしない文章

ボタン・メニュー・戻る / BACK・HELP・LANGUAGE・SETTINGS、入力履歴、aria-label、STATUS、基地マップ、発見済み設備一覧、ENERGY、SUCCESS率、READY / NOT READY、通路状態 NORMAL / DARK / BLOCKED / CLOSED、UNKNOWN / FRESH / STALE、HELPの純粋なルール説明、CAMERA FEEDを簡潔な情報表示のまま保つ。カメラ開始・終了に地の文を追加しない。

## 10. 長さと改行

通常の出来事は1～3文、区画説明は2～4文を基本とする。通常行動のログ量は従来のおおむね1～2倍以内を目安とする。短い文の間は改行でき、必要なら空行で間を作る。長い段落を避け、320px幅のスマートフォンで読むことを前提にする。

## 11. 調査文章

回収・携帯品使用・設置・遠隔起動・固定設備・発進の各確認で、対象に触れる描写、利用可能性の認識、短い質問を意味のある単位で管理する。「確認する」「見る」「調べる」だけを反復しない。質問は「解除するか？」「回収するか？」「発進するか？」など簡潔にし、ボタンは「はい／いいえ」「YES / NO」を維持する。実行済み・辞退も主人公の認識や動作で表す。前提不足と実行済みでは質問を出さない。補給量・上限・回数は説明中でも独立した機械的表示で残す。

## 12. 移動文章

NORMALは非常灯と生命維持装置、DARKはスーツライトなど、消費理由を体験として書く。BLOCKEDでは塞がれた通路を認識し、進入完了と書かない。緊急退避は通常移動と区別し、移動先と消費を明示する。通路を恒久修復したとは書かない。CLOSEDは「隔壁は完全に閉じている。ここから先へは進めない。」という認識と `CLOSED / ENERGY消費なし` を分ける。

## 13. 遭遇文章

ロボットの動きやセンサーを主人公の視野で描き、機械的な認証・警告情報はAIから伝える。緊急退避は成功・失敗を別の描写にする。成功率25%・消費・失敗GAME OVERは独立した機械的情報として残す。

## 14. 操作結果

操作の描写、結果の知覚、明示的なゲーム状態を分離する。消費でENERGYが尽きる場合、回収・設置・使用が完了した描写を先に出さない。取得物資・消耗品使用・補給使用済みの情報を明示する。

## 15. GAME OVER / GAME CLEAR

GAME OVERの直前には警告音や表示の消失など短い地の文を置き、AIが枯渇を通知する。過度に残酷にしない。GAME CLEARは月面を離れる船、遠ざかる基地、地球への航路などを静かに締める。終了ラベルは明示する。再開手段はUIに任せ、情景に説明書の文章を混ぜない。

## 16. 禁止事項

全文章に「私は」を付ける、過度な感情説明、長い比喩、架空の装置や専門用語の追加、未決定の基地名・規模・事故原因・乗員の死亡状況・主人公やAIの設定の確定をしない。文体変更でENERGY・turn・RNGや呼び出し順・通路・敵・Action・前提条件・アイテム・帰還条件・監視・鮮度・State遷移・HELP・確認動作・BACK・ページング・言語切替・localStorage・マップ・施設配置を変更しない。

## 17. 日本語・英語対応

ja/enでゲーム上の情報量を一致させる。描写は自然な各言語で書き、ログに他言語の専用文を混入させない。共通システム語（ENERGYなど）は使用できる。既存の翻訳構造とRoom・ItemId・プレースホルダーの型安全性を守り、sentence1等の意味のない分割キーを増やさない。Action・対象単位など意味のある関数・レコードにまとめる。

## 18. 文章追加時のチェックリスト

- 主人公が知り得ない情報を書いていないか。
- 「私」を使いすぎていないか。
- AIと主人公の文章が区別でき、AIの接頭辞が正しいか。
- システム情報を小説表現で隠していないか。
- 一文が長すぎず、スマートフォンで読みやすいか。
- 未決定設定を確定していないか。
- ja/enで情報量が一致し、他言語の専用文が混入していないか。
- ゲームルール・State・RNGの結果や呼び出し順へ影響していないか。
- 同じ表現を繰り返しすぎていないか。
- HELP・STATUS・CAMERA・ラベルを簡潔な情報表示のまま維持したか。
- 確認質問、はい／いいえ、前提不足・実行済みの動作を維持したか。

## 19. 探索・回避の短い例

```text
壁の表示を読む。ここは医療区だ。
金属音が東から聞こえる。
AI：東方向にロボット反応。距離2。
誘導装置を起動する。短い音が通路へ響く。
制御表示が切り替わり、隔壁が動く。
AI：A1–B1 / CLOSED。閉鎖は3ターン後に自動復旧。
```

未知区画の名前は表示を読むなどの情報取得後に書く。地図だけでロボットや物資の現在地を語らない。英語でも I / my の一人称とAI:の区別を維持する。
