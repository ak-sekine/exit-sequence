# Exit Sequence 最初のゲームプロトタイプ仕様書

## 1. 本書の位置づけと目的

本書は、最初のゲームプロトタイプを実装するための暫定仕様である。完成版のボリュームやシナリオを作り込むことではなく、次のコアループがゲームとして成立するかを確認する。

```text
監視する → ルートを判断する → ENERGYを消費して移動する
→ 敵・通路状態が変化する → タスクを実行する
→ 必要ならENERGYを補給する → 状況に合わせて次のルートを選ぶ
→ 帰還条件を満たして脱出する
```

特に以下を検証する。

- ENERGY管理に判断が生まれるか
- 複数ルートを選択する意味があるか
- 通路状態の変化がルート選択に影響するか
- 敵の巡回によって迂回判断が発生するか
- 監視カメラにENERGYを使う価値があるか
- ENERGY補給への寄り道が判断として成立するか
- 成功率とENERGY消費を比較する仕組みが分かりやすいか
- 9区画の規模感が適切か

**本書の数値・配置・構成・イベント数はすべて調整前提であり、完成版仕様として固定しない。** コアループをプレイ可能にした初回実装の仮決定は第23章に記録する。記載内容すべての完成版実装を意味しない。

## 2. プロトタイプ用基地マップ

現在のプロトタイプは9区画の3×3固定グリッドを使用する。上下左右のみ、双方向の12通路で接続し、斜め接続はない。接続は固定し、通行可否は通路状態で表す。

```text
[居住]─[医療]─[観測]
  │      │      │
[倉庫]─[管制]─[電力]
  │      │      │
[研究]─[整備]─[発着]
```

正式名は居住、医療、観測、倉庫、管制、電力管理、研究、整備、発着。基地マップと施設案内では電力管理を電力と短縮する。生命維持と通信は独立区画から削除し、それぞれ居住などの生命維持設備、管制などの通信設備として背景に残す。新たな操作は追加しない。

| 区画 | 役割 |
| --- | --- |
| 居住 | 開始地点 |
| 医療 | 予備バッテリー |
| 観測 | 不要設備停止によるENERGY補給 |
| 倉庫 | 食糧 |
| 管制 | 発進管制解除 |
| 電力管理 | 帰還船用電力 |
| 研究 | 修理部品 |
| 整備 | 帰還船修理 |
| 発着 | 帰還船発進 |

文字UIとゲームループの検証用構成であり、完成版の区画数・最終配置は未決定。

## 3. 区画内部の扱い

各区画を基本的に1つのゲーム上の地点として扱い、必要な場合のみ簡単な設備・アイテム・タスクを配置する。まず区画間のルート選択を検証し、区画内部は細かく作り込まない。

[ゲーム仕様書](game-design.md) 第5.7節の「各区画内部に複数の意味ある地点を持たせる」設計方針は維持する。その構造の追加はプロトタイプ検証後に扱い、本書の簡略化で完成版の方針を変更しない。

### 施設案内（現行プロトタイプ）

区画内部の詳細マップを作らず、目的の施設がどの区画にあるかを確認できるよう、持ち物に固定情報「施設案内」を追加した。基地マップは区画の位置・接続・現在地を示し、施設案内は各区画の主な施設を示す別の参照情報とする。データは `src/map.ts` の Room 単位の `facilityIds`（表示名は `src/i18n.ts`）にまとめる。以下は現行プロトタイプ用の仮配置であり、完成版の確定施設一覧ではない。

```text
> 持ち物 施設案内

施設案内
居住：居室、食堂、共用室
医療：診療室、薬品庫
観測：観測室、機器室
倉庫：資材庫、食糧庫
管制：管制室、通信室
電力：配電室、電源設備室
研究：研究室、保管室
整備：整備室、工具庫
発着：格納庫、発着管制室
```

通常選択は入力と空行を即時確定し、本文を既存の5ms／文字で表示する。ログタップでスキップできる。HELP ONでは `> HELP 持ち物 施設案内` を記録し、施設一覧を表示せず、所在地を調べる参照情報でENERGY消費・進行なしという説明だけを表示する。HELPは自動OFF、元の持ち物画面を維持する。

参照はgame.act()・RNGを呼ばず、ENERGY、turn、現在地、敵位置・直前位置、遭遇、通路状態・更新、監視情報・鮮度、アイテム、帰還条件、補給使用済み、statusを変更しない。固定項目「基地マップ」「施設案内」を所持アイテムより前に置き、合計7件以上は既存ページングを使用する。

各区画内部を実際に移動・探索する仕組みは未実装。部屋の現在地管理、部屋マップ、部屋ごとの調査、施設への直接・自動移動、検索UI、施設選択・詳細説明、新アイテム・タスクは追加しない。

## 4. スタート地点と導入

居住区から開始する。サポートAIが次の内容を簡潔に説明する。

- 基地が致命的損傷を受けていること
- 基地を恒久復旧することはできないこと
- 帰還船を使用して地球へ帰還する必要があること
- 帰還には複数の条件を満たす必要があること

具体的な会話文は実装時の簡易な仮文章でよい。主人公やAIの正式な設定を追加確定しない。

## 5. クリア条件

以下の4条件をすべて満たして発着区へ行き、帰還船を発進するとクリアとする。

| 条件 | 主な場所 | 内容・依存関係 |
| --- | --- | --- |
| 帰還船用電力 | 電力管理区 | 残存電力の配電を変更し、帰還船への給電を可能にする |
| 発進管制解除 | 管制区 | 帰還船の発進ロックを解除する |
| 帰還船修理 | 整備区 | 別区画で取得した修理部品を使用し、帰還船の故障箇所を修理する。部品の仮配置は研究区 |
| 食糧確保 | 倉庫区 | 地球帰還に必要な食糧を回収する |

食糧はENERGYのような逐次消費リソースにせず、帰還条件を満たすアイテムとして保持する。電力確保は残存電力の利用であり、主発電設備の恒久復旧を要求しない。

帰還船自体の所在地は発着区、修理タスクの主な実行地点は整備区として区別する。整備区での作業が船の修理につながる具体的な設備描写は仮文章でよい。

完成版で想定する大条件・サブ条件の構造を、この4条件と部品取得に絞って検証する。完成版の条件一覧や依存関係を確定しない。

## 6. 最終脱出

4条件を満たした状態で発着区へ移動すると「帰還船を発進する」を選択可能にする。実行するとプロトタイプクリアとなる。

条件不足の場合はサポートAIが不足している条件を通知する。

## 7. ENERGY

以下はすべてプロトタイプ専用の調整用仮値である。

| 項目 | 仮値 |
| --- | --- |
| 初期ENERGY | 20 |
| 最大ENERGY | 20 |
| 通常移動 | 1 |
| 軽度な通路障害 | 2 |
| 重度な通路障害 | 3 |
| 監視カメラ利用 | 1 |
| 通常タスク | 1～2程度 |
| ENERGY補給 | +6 |

移動コスト1・2・3はそれぞれの移動の総消費量であり、通常移動1への追加消費ではない。補給後も最大ENERGYを上限とする。

ENERGYが0以下になった場合はプロトタイプではゲームオーバーとする。初期値・上限・各消費値・補給量・ゲームオーバー条件のいずれも完成版の確定を意味しない。タスクごとの消費値は上記の目安から実装時に仮設定する。

## 8. 通路状態

複雑化を避け、通路状態を次の4種類に絞る。

| 状態 | 概要 | 仮の移動コスト |
| --- | --- | --- |
| NORMAL | 大きな問題なし | 1 |
| DARK | 照明停止。スーツ照明が必要 | 2 |
| BLOCKED | 瓦礫や隔壁不良などで通行困難 | 3 |
| CLOSED | 通行不能 | 移動不可 |

移動時は数値だけでなく、ENERGYを消費した理由をログへ表示する。イベント文章は簡易なものでよい。

```text
整備区へ移動。
通路照明が停止している。
スーツ照明を使用した。
ENERGY -2
```

## 9. 初期通路状態

開始時に一部の通路状態をランダムに決定する。接続関係は変えず、最低限クリア不能なマップを生成しない。

クリア条件の地点・修理部品・発着区へ到達できることを含め、クリア可能性を確保する必要がある。具体的なランダム化・検査方式は実装段階で単純な方式から開始してよい。再現性や高度な生成より、毎回ルート状況が少し変わることの確認を優先する。

## 10. 行動によるゲーム進行

リアルタイム時間は使用しない。ゲーム世界に影響する行動を行った場合に内部的な進行値／ターンを1進める。

| 進行させる行動 | 進行させない操作 |
| --- | --- |
| 区画間移動 | ログ閲覧 |
| 設備操作 | ページ操作 |
| クリア条件タスク | 「戻る」 |
| ENERGY補給タスク | 持ち物を見るだけ |
| 監視カメラ利用 | 状態を見るだけ |
| 敵との遭遇時の行動 | メニューを開く・選択候補を見るだけ |

「調べる → 周囲」は簡単な説明を読むだけの操作とし、ENERGY消費・進行は発生させない。逃走による移動は1つの遭遇対処行動として扱い、移動と対処でターンを二重加算しない。

内部ターン数を「残り○ターン」として常時表示する必要はない。

## 11. 通路状態の時間変化

世界に影響する行動の後、一定確率で通路状態を変化させる。単純な状態遷移から開始する。

```text
基本例：NORMAL → DARK → BLOCKED → CLOSED
改善例：BLOCKED → DARK、DARK → NORMAL
```

一方的な悪化だけでなく、一部に改善方向の変化を発生可能にしてよい。世界設定上の厳密な原因より、プレイ中に利用価値の高いルートが変わるかを優先する。必要に応じてAIのログで知らせる。

変化確率・対象通路数・CLOSEDからの回復・プレイ中のクリア可能性を守る方式は実装時の仮決定事項とする。ゲーム仕様書第5.5節の、運だけで理論上クリア不能にしない方針を維持する。

## 12. 敵

敵を1体配置し、正体は仮に「防災ロボット」とする。通常のロボット群は節電のため停止しているが、この1体だけは事故後の非常プロトコルによって動作している、という仮設定を使用してよい。

ゲーム仕様書第3.3節の通常ロボット群の緊急停止と、第5.11節の危険な存在の構想との関係を検証用に整理した設定であり、完成版の例外設定・敵の正体・数を確定しない。

## 13. 敵の移動

世界に影響する行動の後、敵も隣接区画へ移動する。単純なランダム移動を基本とし、不自然な往復を減らすため直前の区画へ戻る確率を下げる程度の調整はしてよい。

高度な追跡AI・経路探索は不要であり、敵がプレイヤーの現在位置を常に把握して追跡する仕様にはしない。初期位置、通路状態による敵の移動制限、移動候補がない場合の扱いは実装時に仮設定する。

## 14. 敵との遭遇

プレイヤーと敵が同じ区画になった場合に遭遇イベントを発生させる。遭遇だけで即ゲームオーバーにしない。最低限、以下を用意する。

| 対処 | 成功率（仮） | ENERGY（仮） | 内容 |
| --- | --- | --- | --- |
| 隠れる | 80% | 1 | 隠れて遭遇をやり過ごす |
| 強行突破 | 60% | 2 | 妨害を突破する |
| 逃げる | 個別の確率は本書で定めない | 選択した通路の移動コストを基本とする | 移動可能な隣接区画を選ぶ |

失敗時は追加ENERGY消費、元の区画または隣接区画への押し戻しなど、簡単なペナルティでよい。具体的な追加消費・移動先は実装時に仮設定する。戦闘システムは作らない。

対処成功後の同一区画での再遭遇抑制や、逃走先での遭遇の扱いも実装時の仮決定事項とし、無限に遭遇処理が連鎖しないよう整理する。成功率・失敗率とENERGY消費は実行前の判断材料としてHELPログで参照可能にする。通常選択肢には対処名のみ表示する。具体的な表示形式はUI共通仕様に従う。

## 15. 監視カメラ

主要な検証対象とし、利用時にENERGYを1消費する。現在地から直接移動可能な各ルートについて確認できる方式とする。AI配下の監視カメラメニューでは区画名のみ表示し、実際に監視した結果ログで最低限以下の情報を表示する。HELPでは監視のENERGY 1、選択した1ルートのみの取得、鮮度ルールを説明し、新しい情報は取得しない。

- 接続先区画
- 敵が確認できるか
- 通路状態
- 推定ENERGY消費

```text
観測区方面
敵：なし
通路：DARK
推定 ENERGY：2
```

未確認の場合は次のように扱ってよい。

```text
敵：UNKNOWN
通路：UNKNOWN
推定 ENERGY：UNKNOWN
```

監視で得るのは確認時点の情報であり、完全な未来情報ではない。全基地の常時把握は行わない。CLOSEDを確認した場合は移動不可と分かる情報を示す。1回の利用で選択ルートだけを取得するか、隣接ルートをまとめて取得するかは実装時に仮設定し、コスト1との釣り合いを検証する。

## 16. 監視情報の鮮度

敵位置・通路状態は進行で変わるため、取得情報を永久に最新として扱わない。最初は「世界に影響する次の行動が行われたら、既存の監視情報は古い情報として扱う」程度の仕組みでよい。

最新・古い情報・未確認を区別できるようにする。「何ターン前」などの詳細な履歴表示は不要。監視そのものも世界を進めるため、監視行動内の世界更新と情報取得の順序は実装時に明示して仮決定する。表示した情報がどの時点のものかと、次の行動までの鮮度が一貫するようにし、監視の価値を検証する。

## 17. ENERGY補給タスク

任意の補給タスクを2個程度配置する。

| 仮配置 | 内容 | 効果 | 回数 |
| --- | --- | --- | --- |
| 医療区 | 予備バッテリーを回収する | ENERGY +6 | 1回のみ |
| 観測区または研究区 | 不要設備を停止し、利用可能電力を確保する | ENERGY +6 | 1回のみ |

2個目の配置は実装上の都合で観測区・研究区のどちらかを選んでよい。直接クリアには不要だが、ENERGYに余裕を作るために寄り道する価値があるかを検証する。

補給タスク自身の消費・成功率・回復処理の順序は実装時の仮決定事項とする。補給量や配置を完成版の値として扱わない。

## 18. アイテム

最低限、修理部品と食糧を用意する。

| アイテム | 仮配置 | 用途 |
| --- | --- | --- |
| 修理部品 | 研究区 | 整備区の帰還船修理条件に使用する |
| 食糧 | 倉庫区 | 帰還条件として保持する |

実装時には必要に応じて既存UI確認用アイテムを削除・置換する。大量のアイテム、複雑なインベントリ、使用対象の選択など今回不要な仕組みは作らない。部品の消費処理や回収タスクのコストは実装時に仮設定する。

## 19. 成功率

最低限の確率システムを用意し、主に敵との遭遇対処、必要であれば一部設備操作に使用する。すべてのゲーム行動に無理に成功率を付けない。まず確率とENERGY消費を比較して選択することが面白いかを確認する。確率値はすべて仮値とする。

ゲーム仕様書第4.2節の「主要な行動には原則として成功確率と失敗確率を設定する」は完成版の方針として維持する。本プロトタイプでは検証範囲を限定し、その方針や完成版の対象行動一覧を変更・確定しない。

## 20. 基本メニューとUI

UI詳細の正本は [UI仕様書](ui-layout.md) とする。2列×3行の共通ルールを使用し、最上位メニューを仮に以下とする。

```text
[調べる >] [移動 >]
[持ち物 >] [AI >]
[設定 >]   [空き]
```

- 調べる：周囲と現在地の設備・対象。設備対象を選んだ時点で入力履歴を確定し、状態説明をログ表示する。必要な場合は確認質問を表示し、はい／いいえなどの簡潔な回答を別入力として記録してから既存タスクを実行する。他の設備は既存の詳細画面の実行選択肢を維持する。調査参照だけでは進行しない。
- 移動：隣接区画。
- 持ち物：基地マップ、施設案内、所持アイテムの順。基地マップと施設案内は開始時から参照できるUI固定項目で、消費可能な items には追加しない。
- AI：状態確認、監視カメラ > → 隣接区画。状態確認は既存の状態表示を再利用し、監視は従来の消費・世界更新・鮮度を維持する。

メインには設備・監視・状態確認・マップを直接置かない。調べる → 状況を知る → 結果に応じて次の行動を選ぶ構造を基本とする。内部 Action / task、数値、前提条件、消費・補給・ターン処理は変更しない。

基地マップは3×3の固定文字図をログに表示する。現在地だけ * を付け、位置と固定接続のみ表示する。敵・通路状態・正確なコストは開示しない。参照はENERGY・ターン・乱数・敵・通路・監視鮮度を変更しない。

複数階層は pendingInput で保持し、最終選択時に一行へまとめる。例：
`> 調べる 周囲`、`> 調べる 配電盤`、`> 帰還船へ配電する`、`> AI 状態確認`、`> AI 監視カメラ 医療区`、`> 持ち物 基地マップ`、`> 持ち物 施設案内`。
調査対象を選択した時点で入力履歴を確定し、状態説明をログ表示する。必要な場合は確認質問を表示し、はい／いいえなどの簡潔な回答を別入力として確定してから既存タスクを実行する。HELPは `> HELP 調べる 配電盤`、`> HELP AI 監視カメラ 医療区` のように実際の階層を反映する。一件参照でOFF、非進行、同じ画面、5ms／文字、タップスキップを維持する。

戻るは詳細 → 調べる、監視対象 → AI、調べる／AI／持ち物／移動 → メインと一段ずつ戻る。履歴へ記録せず、HELP ONを維持する。通常選択肢の > は対象一覧・カテゴリ・別の選択肢階層を開くサブメニューだけに付ける。

### 調査結果と確認回答

調査対象（予備バッテリー、配電盤など）には `>` を付けない。対象を押した時点で `> 調べる 対象名` と空行を即時確定し、調査結果を5ms／文字で表示する。確認が必要なら最後に質問を出し、選択肢は「はい」「いいえ」とする。

```text
> 調べる 予備バッテリー

予備バッテリーを確認した。
回収すると ENERGY が6回復する（上限20）。1回のみ。
回収しますか？
> はい
```

回答は `> はい`／`> いいえ` と空行を即時記録し、調査入力と一行にまとめない。「はい」は既存medicalタスク（+6、上限20、1回のみ）を実行する。「いいえ」は短い結果ログを出して調べるへ戻り、ENERGY・ターン・敵・通路・監視鮮度・タスク・乱数を変更しない。下部の戻るはログに残さず、調べるの入力経路を維持する。回収済みなら調査結果だけを出し、はい／いいえを表示しない。

HELPでは `> HELP 調べる 予備バッテリー` を記録し、実行済み状態を含む説明だけを表示する。確認画面には進まず、状態不変・自動OFF・元の調べる画面を維持する。本文表示中は全操作を無効化し、ログタップのスキップを維持する。確認文はタスク別設定として持ち、今後の設備へ拡張できる。

現在地、現在ENERGY／最大ENERGY、帰還条件4項目の達成状況を最低限ログへ表示する。

```text
LOCATION : 居住区
ENERGY   : 14 / 20
RETURN STATUS
POWER    : NOT READY
```

## 22. ゲームオーバーとリスタート

ENERGY <= 0でゲームオーバーとする。ゲームオーバー後は最初から再開できる手段を用意する。ブラウザ再読み込みを必須操作にせず、ゲーム内から再開始できることが望ましい。

再開始時はENERGY、位置、帰還条件、持ち物、補給タスクの実行状況、敵、通路、監視情報などのプレイ状態を初期化する。詳細なセーブ／ロードは対象外。

## 23. ランダム要素と実装時の仮決定事項

| 最低限ランダム化する候補 | 最初はランダム化しなくてよいもの |
| --- | --- |
| 初期通路状態 | 基地マップ |
| プレイ中の通路状態変化 | クリア条件の配置 |
| 敵の移動先 | 必須アイテムの配置 |
| 成功率判定 | 区画そのもの |

ゲームループの検証を優先する。高度なランダム生成や再現性のための仕組みは作り込まない。

本書で値や方式を指定していない以下の詳細は、実装時に単純な仮仕様を選び、完成版と区別して記録する。

- 初期通路状態の割合・クリア可能性の検査方式
- 通路変化の確率・対象数・閉鎖からの回復・進行中の行き詰まり防止
- タスクごとの消費・成功率・取得や補給の処理順
- 敵の初期位置・移動制限・遭遇成功後の処理・失敗ペナルティ
- 監視1回の取得範囲・情報取得と世界更新の順序
- 行動結果、ENERGY判定、通路変化、敵移動、遭遇、クリア判定の処理順

これらは今回勝手に完成版仕様として補完しない。監視が即座に無価値になる処理、遭遇の無限連鎖、運だけによるクリア不能を避ける形で整理する。

### 実装時の仮決定（最初のゲームプロトタイプ）

以下は検証用の仮採用であり、完成版仕様への昇格ではない。

- マップは本書の9区画・12本の双方向接続。開始時、異なる4通路を選び、DARK／BLOCKED／CLOSEDから等確率で状態候補を選ぶ。他はNORMAL。候補ごとに幅優先探索し、全9区画の到達可能性を失う変更を棄却する。開始地点は居住区。
- 世界更新ごとに30%の確率で1通路を変更候補にする。NORMAL→DARK、DARK→NORMAL／BLOCKED、BLOCKED→DARK／CLOSED、CLOSED→BLOCKED。2候補がある状態は等確率。NORMAL以外は最大6通路に抑える。初期生成と同じ全区画到達チェックで閉鎖による行き詰まりを防止する。ENERGYを使い切るプレイヤーの選択や遭遇失敗によるGAME OVERは防止対象にしない。
- 電力・管制・部品取得・食糧取得は各ENERGY 1、修理は2。いずれも成功率100%。修理時は部品を消費し、食糧は保持する。部品不足・実行済みタスク・未達成条件での発進・CLOSED移動は消費もターン進行もなし。
- 補給は医療区の予備バッテリーと観測区の不要設備停止。各1回、消費0、成功率100%、ENERGY +6（最大20）。上限で切り捨てられても使用済みとなる。発進は消費0、1ターン進行、GAME CLEAR後の世界更新は停止する。
- 行動順は「有効性・前提確認 → 消費 → ENERGY <= 0判定 → 移動・取得・タスク・補給・遭遇結果 → 内部ターン+1 → 通路更新 → 敵移動 → 遭遇判定 → 監視の場合は情報取得 → UI更新」。消費で0になったら結果・ターン・世界更新を反映せずGAME OVER。遭遇失敗の追加消費にも同じ判定を適用する。帰還船発進は条件確認後にCLEARとし、ターンだけ進める。
- 防災ロボット初期位置は研究・整備・管制から等確率。CLOSED以外の隣接区画からランダムに選ぶ。直前以外の候補があれば80%でその集合から選び、残り20%は全候補から選ぶ。候補なしなら留まる。プレイヤーが敵所在区画へ進入した場合は巡回を中断して遭遇し、敵が移動して回避扱いにならないようにする。プレイヤーの追跡はしない。
- 隠れる80%／消費1、強行突破60%／消費2。失敗時は追加ENERGY 1で離脱し、即死ペナルティは設けない（電力枯渇は通常どおりGAME OVER）。逃走は成功率100%で選んだ通路コストを消費。いずれも1ターンのみ進み、その世界更新では再遭遇を抑制する。次の通常行動から再び遭遇判定する。処理は再帰させない。
- 監視は選んだ1ルートのみ、消費1。通路更新・敵移動後の状態を取得するため、取得直後は最新。次の有効な世界行動で古くなる（別ルート監視を含む）。取得元・接続先ごとに記録し、未確認／最新／古いを区別する。移動メニューのボタンは区画名のみ表示し、HELPログに鮮度付きの取得時点の情報を表示する。未監視の通路は状態・正確なコスト・敵を開示せず、HELPではUNKNOWN／未確認と範囲1～3のみ表示。CLOSEDだけは現在の移動不可として無料表示する。古い情報は現在の安全性を保証しない。
- 初回はゲーム開始画面。GAME OVER／GAME CLEAR後は「最初から」で全ゲーム状態を初期化し、通路・敵位置を再生成する。終了後の世界行動は受け付けない。UI確認操作とページ操作・戻る・HELPは消費・進行なし。HELPは次の1件を調べる一時モードとし、1回参照すると自動OFF。戻る・ページ操作・メニュー遷移・HELP対象外の操作では待機中のON状態を維持する。再開始ではOFF。対象選択をやめる場合は下部の戻るを使用する。
- ログ・入力履歴・選択肢の寸法・固定ナビゲーションは [UI共通仕様](ui-layout.md) に従う。
- 乱数はGameに注入できる関数に集約。新しいテスト基盤は導入せず、Node.js 22.18以上のTypeScript実行と標準node:testで検証する（npm test）。

## 27. 現行実装：ja/en切替

現行プロトタイプは日本語（ja）／English（en）の切替を実装している。開始画面のLANGUAGEとゲーム中の設定／SETTINGS → 言語／LANGUAGEから共通の選択画面を開く。表示言語はStateと別に管理し、内部Room・Task・Action・PassageなどのIDとゲームルールは言語非依存とする。翻訳のためにENERGY値、成功率、処理順、乱数呼び出し順、敵移動、通路変化、タスク、監視、クリア条件を変更しない。

`src/i18n.ts` に両言語のUI・入力履歴・ゲーム結果・HELP・aria・区画説明・区画名・マップ略称・施設名を集約し、型付きのキーとプレースホルダーで表示文を生成する。ゲーム出力は呼び出し時の言語を受け取り、Game自身に言語状態を持たせない。既存ログを再翻訳せず、新しい出力だけに選択言語を適用する。

言語設定は `exit-sequence-language` に保存し、初期言語は有効な保存値 → ブラウザ言語（ja / ja-*は日本語、その他は英語）→ 日本語フォールバックの順で決める。ストレージ失敗はゲームを停止させない。設定操作はログ追加・世界進行・RNG使用なし。タイプ表示中は言語選択も無効化する。戻るは一階層ずつ。詳細は [UI仕様書の言語設定](ui-layout.md#15-日本語英語の表示設定) を参照する。

英語UIも320px、2列×3行、44px高、13px文字、既存のページング・下部ナビゲーションを維持する。英語マップはHAB / MED / OBS / STO / CTL / PWR / LAB / MNT / PADの3文字略称を使う。施設配置と施設数は日本語と同じで、英語施設案内も参照のみとする。
