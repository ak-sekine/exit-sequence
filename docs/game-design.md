# Exit Sequence ゲーム仕様書

## 1. 本書の位置づけ

本書は、現時点で決定したゲーム内容と今後の設計方針を整理する。記載の区分は次のとおり。

| 区分 | 意味 |
| --- | --- |
| 決定済み仕様 | ゲームの前提として採用する内容。実装済みを意味しない |
| 設計方針 | 検討中の方向性、想定する仕組み、候補。詳細や採用が確定していない内容 |
| 未決定事項 | 数値、具体的な内容、方式などを今後決める項目 |

UI詳細の正本は [UI仕様書](ui-layout.md) とする。本書ではゲームとの関係のみを記し、レイアウトや実装値を再定義しない。

コアループ検証用の暫定的な具体値・構成・実装範囲は [プロトタイプ仕様書](prototype-spec.md) に分けて記載する。同書の仮仕様は本書の未決定事項を確定するものではなく、検証後に正式採用すると判断した内容だけを本書へ反映する。

### 現行リポジトリとの関係

現行の `src/main.ts`、`src/style.css`、`index.html` は、ターミナル風のログ、通常メニュー、持ち物のページ分割、下部ナビゲーションを備えたUIサンプルである。通常メニューの持ち物以外の項目と持ち物の各項目は、選択した名前をログへ追加する処理になっている。

ENERGY管理、行動の成功・失敗判定、設備利用・修理、帰還条件、敵、監視などのゲームロジックは未実装。現行サンプルのアイテム名・個数、行動名、冒頭ログは、確定したアイテム一覧、基地マップ、シナリオとして扱わない。本書の決定済み仕様も実装済みを意味しない。

本書の数値例・画面例・設備や行動の例は、明示的に決定済みとしたものを除き、仕様値や採用一覧として固定しない。

## 2. 決定済み仕様：ゲーム概要と舞台

- タイトルは **Exit Sequence** とする。
- スマートフォンを主対象とする、ターミナル風UIのシンプルな脱出ゲームとする。
- 舞台は月面基地。隕石衝突によって長期運用不能な致命的損傷を受けている。
- 主人公は基地に残された唯一の人間である。
- 壊れた基地に残る設備・電力・物資を利用して帰還準備を整え、帰還船を使用可能な状態にして月面から脱出し、地球へ帰還することを目的とする。
- 主発電システムを完全復旧して基地で生活を継続することはできない。基地全体の正常化や主発電設備の恒久復旧は、基本的なクリア目標にしない。
- 現時点では隕石事故そのものに大きな陰謀や謎を設定しない。
- 事故後の限られたリソースを管理しながら脱出することをゲームの中心とする。

## 3. 決定済み仕様：登場人物と基地の状態

### 3.1. 主人公

プレイヤーが操作する、月面基地にいる唯一の人間。基地内を探索し、設備の操作・修理・移動などを行う。名前、性別、年齢、職種などの詳細プロフィールは未決定。

### 3.2. サポートAI

主人公のバディとしてゲーム全体を通して同行するAI。通常時は基地設備や各種ロボットを管理・操作し、人間の活動を支援する。事故後も最低限のシステム上で稼働し、次の支援を行う。

- 基地や設備の状態説明
- 行動候補の提示
- 成功確率・失敗確率などの分析
- 危険の警告
- ロボットや設備に関する情報提供
- 主人公との会話

基本的には事務的で冷静な口調を維持し、ときどき皮肉や乾いた冗談を含ませる。人間のように感情的に話すキャラクターにはしない。主人公を強く馬鹿にしたり、不快になるほど責めたりしない。特に危険な状況では皮肉を抑え、簡潔で正確な情報提供を優先する。

AIの名称、詳細な過去・設定は未決定。

### 3.3. ロボットと電力供給

基地には整備・運搬・点検などを行う複数のロボットが存在する。通常時はサポートAIが基地設備とロボット群を統括し、多くの作業を担当するため、人間がすべての作業を直接行う運用ではない。

隕石衝突で主発電システムが使用不能となり、基地は非常用電源へ移行している。電力供給は次を優先する。

- 主人公の生存に必要な設備
- 最低限の生命維持
- 非常照明
- サポートAIの最低限の機能
- 必要最低限の通信・制御設備

ロボット群は電力節約のため緊急停止している。完全に使用不能という設定にはしない。主人公はサポートAIの支援を受け、自分で基地内を行動して脱出条件を整える。

必要な設備や経路を局所的に修理・利用することと、基地を長期運用可能に復旧することは区別する。電力関連の作業候補は、第5.6節の設計方針で扱う。具体的な発電方式、電力量、設備構成は未決定。

ロボットの種類、台数、能力は未決定。一時的な再起動をゲーム要素にする構想は第5章で区別して扱う。

## 4. 決定済み仕様：基本ゲームシステム

### 4.1. ENERGYと行動

中心となるリソースは **ENERGY** とする。主人公がゲーム世界に対する行動を行うと、内容に応じてENERGYを消費する。

単純なリアルタイムの時間制限は採用しない。文章を読んだり考えたりする時間にはENERGYを消費せず、ゲーム内の行動を選択したときにリソースを消費する方式とする。

ログ閲覧、ページ操作、メニューの「戻る」、持ち物確認など、ゲーム世界に影響を与えないUI操作ではENERGYを消費しない。持ち物の確認と、ゲーム世界に影響を与えるアイテム使用などは区別する。個別行動の消費値は本書では定めない。

初期ENERGY、最大ENERGY、行動ごとの消費量は未決定。ENERGYが0になった場合のゲームオーバーは、決定済みではなく第5章の設計方針とする。

### 4.2. 成功確率・失敗確率

ゲーム上の主要な行動には、原則として成功確率と失敗確率を設定する。確率をプレイヤーに隠さず、選択時の判断材料として提示する。

成功率・失敗率とENERGY消費を判断材料にする。単純に運だけで結果が決まるゲームにはしない。ゲーム全体の判断構造は第5.13節に整理する。

各行動の成功・失敗による具体的な結果と、確率や消費量のUI表示方法は未決定。

### 4.3. ENERGY回復とランダム要素

ENERGYは消費するだけでなく、ゲーム中に回復できる要素を設ける。具体的な回復方法、回復量、確率は未決定。

毎回まったく同じ攻略にならないようランダム要素を導入する。ただし、完全なランダム生成を中心にはしない。ランダム化する対象の候補と設計上の方向性は第5章に記す。

### 4.4. 帰還条件と食糧

クリア条件は単一の作業ではなく、複数の大条件と、その下にあるサブ条件を満たす構造とする。具体的な条件一覧は第5.6節の設計方針と区別する。

食糧は、月面から地球までの帰還中に必要な物資であり、帰還船を出発可能にするための必須アイテム／条件とする。ENERGYのような逐次消費リソースとして管理しない。種類、必要量、配置方法、酸素や水を同様に個別アイテム・条件として扱うかは未決定。

### 4.5. タスクの2系統

| 系統 | 役割 |
| --- | --- |
| メインタスク | 帰還に必要なクリア条件・サブ条件を満たす作業 |
| ENERGY補給タスク | クリア条件自体に直接含まれない任意タスク。成功するとENERGYを補給したり、今後の消費を軽減したりできる |

帰還船への電力確保と、主人公のENERGY補給は目的を区別する。具体的なタスクの割り当ては未決定。

## 5. 設計方針：検討中の仕組みと進行

本章は方向性・構想を示すものであり、個別機能の詳細や数値を確定しない。

### 5.1. ENERGYが0になった場合

ENERGYが0になった場合はゲームオーバーにする方向で検討している。判定の詳細は未決定。

### 5.2. 情報や道具による成功率の改善

探索、情報入手、工具や設備の利用によって行動の成功率を改善できる仕組みを想定する。例えば次のような準備によって、当初は成功率が低い行動の安全性を高められる構造を目指す。

- 状況を詳しく調べる
- 適切な工具を入手する
- サポートAIから追加情報を得る
- ロボットを利用する

プレイヤーが、ENERGYを追加消費して安全性を高める、ENERGYを節約して低い成功率に賭ける、別の方法を探す、といった判断を行えるようにする。改善条件や上昇幅は未決定。

### 5.3. ロボットの一時的な再起動

限られたENERGYを消費してロボットを一時的に再起動し、特定の作業を行わせるゲーム要素にできる余地を残す。具体的な作業、再起動条件、消費量、稼働の詳細は未決定。

### 5.4. 回復に伴う判断

ENERGY補給タスクの候補として、未使用設備の停止、予備電源の回収、蓄電設備の再接続、ロボット用電源の転用、太陽電池などの補助電源の利用を考える。採用するタスク、成功率、報酬量は未決定。

補給タスク自体にもENERGY消費や失敗リスクを持たせられる。「ENERGYを回復するためにENERGYを使って挑戦するか」という判断を作る。回復手段にはランダム性を含めてもよく、余裕が生まれれば追加探索などが可能になる構造を想定する。

完全に運任せで行動不能にならないよう、判断・探索・準備で回復の可能性や安全性を高めるとともに、安全性の高い小規模な回復方法を用意する方向も検討する。

### 5.5. ランダム化の候補とクリア可能性

現在想定するランダム要素の候補は次のとおり。すべての候補を採用すると確定したものではない。

- 一部アイテムの配置
- 一部設備の故障状態
- 一部通路の初期状態
- ENERGY回復要素
- 行動の成功・失敗判定
- 一部イベント

マップの接続関係は基本的に固定し、通路や設備の状態を変動させる方向とする。運が悪いだけで理論上クリア不能になる設計は避ける。具体的なアルゴリズムやクリア可能性を確保する方法は未決定。

### 5.6. 脱出までの大枠

帰還船による地球帰還を目的とし、大条件ごとに複数のサブ条件を持たせる方向とする。以下は構造を説明する概念例であり、大条件・サブ条件の具体的な一覧を確定しない。

| 大条件の想定例 | サブ条件の概念例 |
| --- | --- |
| 帰還船用の電力確保 | 利用可能な蓄電設備の確保、配電経路の切り替え、帰還船への給電ライン接続 |
| 帰還船の修理・起動準備 | 損傷確認、必要な部品・工具の確保、必要箇所の修理 |
| 発射・帰還管制の解除 | 管制設備の利用可能化、安全ロック解除、帰還に必要な制御情報の設定 |
| 帰還に必要な物資の確保 | 必要な食糧の確保、帰還船への持ち込み |

条件の詳細、順序、依存関係、必要アイテム、帰還船の詳細は未決定。電力確保は残存設備の利用を目的とし、主発電設備の恒久復旧を要求しない。

発電・電力関連区画では、残存する非常用電源の確保、蓄電設備の利用、配電経路の切り替え、不要設備への給電停止、帰還船への給電経路確保を行う方向とする。具体的な作業一覧、発電方式、電力量、設備構成は未決定。

### 5.7. 区画と内部地点

基地は複数の大きな区画で構成し、各区画の内部に2～3個程度の意味のある場所を持たせることを基本方針とする。この個数は設計上の目安であり、固定値ではない。

例えば居住区には居室・食堂・備蓄庫、整備区画には作業室・ロボット格納庫・部品庫が考えられる。区画名・内部地点の採用一覧は未決定。

内部地点を独立させる基準は、そこで異なる調査・判断・イベント・設備利用などが発生するかとする。ゲーム上の判断や目的がない廊下・入口・途中地点を細かくノード化しない。

同一区画内の通常の場所移動は原則としてENERGYを消費しない。ただし減圧・瓦礫・故障隔壁など、明確な危険を伴う移動はゲーム上の行動としてENERGY消費や成功判定を持たせてもよい。

### 5.8. 基地マップと複数ルート

目的地への複数ルートを用意する。単純な一重リングに限定せず、外周と内周を持つ二重リング状の構成や、中央側を通るショートカットを有力な設計案とする。

現在の通路状態、ENERGY残量、敵の位置、得られている情報を考慮し、その時点で利用するルートを選ぶゲームを目指す。単に最短経路を覚えることを中心にしない。

最終的な区画数・接続関係は未決定。以前の7区画案を確定マップとして扱わず、二重リング化する場合は区画数そのものを再検討する。

### 5.9. 移動イベントとコスト予測

しらみつぶしに全地点を探索することにもリスクを持たせる。移動のENERGY消費は数値だけで示すのではなく、事故後の基地を移動する際に生じた具体的なイベントの結果として表現する。

| イベントの例 | ENERGYを使う理由の例 |
| --- | --- |
| 非常灯停止 | スーツ照明の使用 |
| 温度低下 | スーツヒーターの使用 |
| 微小減圧 | 生命維持出力の増加 |
| 隔壁故障 | 補助モーターの使用 |
| 瓦礫 | パワーアシストの使用 |
| 通信不良 | AIとのリンク維持への追加電力 |

イベント一覧・消費値は未決定。同一区画内の通常移動の扱いは第5.7節に従う。

通路状態によって移動コストを変え、十分な情報があればAIがある程度推測できるようにする。情報取得によって予測可能にし、完全に見えないランダム値にはしない。例えば「推定 ENERGY 1～2」の範囲表示も候補だが、この数値とUI形式は確定しない。

### 5.10. 通路状態と行動による進行

同じ通路でも常に同じ状態とは限らない。接続関係は基本的に固定し、通路・設備の状態を変える。状態の候補は正常、照明停止、隔壁不調、瓦礫、低温、微小減圧、通信不安定、通行困難、通行不能など。具体的な状態一覧・遷移は未決定。

プレイ開始時には一部通路の初期状態を変化させ、毎回同じ最適ルートにならないようにする。プレイ中も、世界に影響を与える行動を重ねることで進行度・ターンのような内部値を進め、状態を変動させる方式を想定する。文章を読む実時間や、ログ閲覧・持ち物確認・ページ操作・メニューの戻るなどでは進行させない。

進行に伴って通路の悪化、隔壁の閉鎖、減圧の進行、設備停止などが起こり得る。一方、主人公の作業で通路修復、瓦礫撤去、電力供給、隔壁制御の復旧など、局所的に状態を改善できる場合も設ける。

単純な「残り○ターン」のカウントダウン表示を中心にはせず、AIの警告や発生イベントで基地の劣化を表現する。時間／ターン進行のアルゴリズム、劣化頻度、状態遷移は未決定。

### 5.11. 移動する敵と遭遇

複数ルートを選ぶ意味を強めるため、基地の区画・ルートを移動する敵対的・危険な存在を導入する方向とする。プレイヤーは位置を推測・確認しながら遭遇を避ける。

正体の候補は誤作動した警備ロボット、制御を失った作業ロボット、自律防災システム／防災ロボットなど。明確な悪意は必須ではなく、事故による認証異常や安全プロトコルの誤作動で、結果的に主人公を妨害する存在でもよい。通常のロボット群の緊急停止との関係も今後整理する。正体、数、移動アルゴリズム、移動頻度は未決定。最初の実装では1体から検討できるが、確定値ではない。

遭遇を即ゲームオーバーにはしない方向とし、確率＋ENERGYのシステムを利用して対処できるようにする。隠れる、強行突破、隔壁操作、別経路への逃走、設備・ロボットの利用などが行動候補となる。

各対処行動には成功率・失敗率、ENERGY消費、成功時・失敗時の結果を持たせられる。具体的な遭遇ルールと数値は未決定。ENERGYや複数のサブタスクを消費し、敵そのものを停止・無力化する任意攻略も検討する。

### 5.12. 監視カメラと情報の鮮度

監視カメラを、ENERGYを消費して情報を得るシステムとして利用する。敵の位置確認に加え、カメラと基地センサーからAIが次を分析できるようにする。

- 敵の有無・位置
- 通路の障害、隔壁の状態、瓦礫などの状況
- 確認可能な環境異常
- そのルートを利用する場合の推定ENERGY消費

監視システムは移動前にルートの安全性とコストを評価するための情報取得手段とする。アクセス自体にENERGYを消費し、「ENERGYを使って安全な情報を得るか、節約して未確認のルートへ進むか」というトレードオフを作る。

確認範囲の候補は現在地と隣接区画、指定区画単位、外周／内周など一定範囲。利用コスト・範囲は未決定で、全基地を低コストで常時完全把握できる仕様にはしない方向とする。

敵位置や通路状態は行動・進行で変化するため、取得情報には「確認時点」が存在し、永久に正しいとは限らない。有効期間、何ターンで古くなるか、古い情報のUI表示は未決定。

監視設備にも通常稼働、低電力、通信断、故障、復旧可能などの状態を持たせられるが、具体仕様は未決定。

### 5.13. ゲーム全体の判断構造

ゲームの中心を、**限られたENERGYを「行動」「移動」「準備」「情報取得」のどこに配分するか判断すること**として整理する。主に次の判断を生む構造を目指す。

- どのメインタスクから進め、どのサブ条件をどの方法で満たすか
- ENERGY補給のために寄り道するか
- 成功率を上げるために事前準備するか
- どのルートを使い、通路状態を調べてから移動するか
- 敵を避けるために迂回するか
- 監視カメラにENERGYを使うか
- ロボットなどを起動して安全性を上げるか

## 6. 決定済み仕様：UIとの関係

ゲームシステムは [UI仕様書](ui-layout.md) の共通ルールを前提として構築する。

- 上部のログ領域
- 2列×3行、1ページ最大6個の通常選択肢
- 選択肢とは別の下部領域にある「戻る」とページナビゲーション
- 通常選択肢では、実際に別の選択肢メニューへ遷移する場合のみラベル末尾に ` >` を表示

下部ナビゲーションの「戻る」「＜」「＞」は、通常選択肢の ` >` 表示ルールの対象外とする。詳細はUI仕様書の第5～9章を参照する。

サポートAIとの会話、設備の状態、行動の成功・失敗結果などは原則としてログ領域へ表示する。成功率、失敗率、ENERGY消費の具体的なUI表示方法は未確定であり、本書では固定しない。
