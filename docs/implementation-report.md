# 原因発見プロトタイプ：実装と評価

最新origin/main `9fe3d7892209aef3e25e9706dc05a77744b39820`からmain上で実装。31 Scene / 94 Choiceを15 Scene / 30 Choiceへ整理した。3問題、初見5～10分を目安とする。時間は未実測。

## 各問題の情報と因果

| 段階 | 問題1：扉 | 問題2：バルブ | 問題3：電力 |
| --- | --- | --- | --- |
| 初期観察 | 電源緑、モーターが動く、扉が少し動いて停止。圧力は高／低 | 冷たいレバーが動かない。外から原因は見えない | 起動で針が上限、OVERLOAD。充填機とリフトが同時に動いていた |
| 追加観察 | 歯車が動き故障灯なし。低い側へ空気が流れる | カバーを開けると軸そのものに氷。突起が氷に当たり停止 | OVERLOADを「同時に使う電力が多すぎる」と説明。一台ずつなら上限以下 |
| 詳細観察 | 点検窓の大小の矢印。高い側の空気が扉を押し戻す | 氷が軸と枠の間をふさぐ。棚にヒーターと工具 | 二台と一台の比較。充填機は必要、空のリフトは不要 |
| AIヒント1 | モーター正常、左右の表示と空気を見る | 冷たいだけでは断定不可。カバーを開けて軸を見る | 故障灯なし。OVERLOAD説明と二台を見る |
| AIヒント2 | 高い圧力の空気が強く押す。故障ではない | 見えている氷が動きを止める。力不足ではない | 一台なら上限以下、二台なら超過。同時に使いすぎ |
| 最終ヒント | 圧力差が原因。均圧して開閉ボタン | 氷が原因。ヒーターで温め、消えてからレバー | リフト停止か順番運転で同時の使いすぎを避ける |
| 原因 | 左右の圧力差が扉を押し戻す | 軸に付いた氷が物理的に動きを止める | 二台同時の使用量が電源の上限を超える |
| 対処と結果 | 均圧で表示と矢印がそろう。まだ閉じている。次のボタンで同じモーターが扉を開く | ヒーターで氷が水滴へ。まだレバー未操作。次の操作で同じ軸が回り空気が流れる | 不要リフト停止で空気だけ満たす、または待って順番に両方完了。針は上限以下でブレーカー維持 |
| 間違った操作 | ボタン再押下でも圧力差は残り扉は停止 | 工具で回しても氷は残り金属がきしむ。「力の問題じゃないな」 | 同時再起動でも超過とOVERLOAD。故障灯は消えたまま |

科学知識ゼロでも、扉は詳細観察で空気の押す力、バルブはカバーで見える氷と接触、電力は追加観察の日本語／英語説明と単独試験から原因が分かる設計。AIヒント2で平易に原因を明言する。早くヒントを聞いた場合もヒント2で実際の追加・詳細点検を描く。見えない内部原因だけをAIが断定しない。

対処を思いつかなくても、最終ヒントが具体的な操作まで示す。その段階まで使えば、外部の科学知識なしでCLEARへ進める。解決状態の変更はプレイヤーの操作で行い、ヒントだけで自動解決しない。ヒントに消費、負傷、終了、評価表示はない。知識がある人は追加説明とAIを省略し、観察から対処へ進める。

## 調整と文体

cluesのinitial / inspect / deeper / hintsの3段階をデータとして共有。配置やヒントの具体性を変更でき、文章全面書換えや巨大な汎用エンジンは不要。型付きobservation / hintLevel / resolutionを3問題で共通化。複雑な準備、資源、アイテム収集、試行回数と総当たりのコストは撤去。items.tsには現場の設備説明だけを残す。

主人公は短文で状況を先に伝え、怖がりながら軽口を言い、失敗に悔しがり成功に喜ぶ。AI：/AI:は正確な情報のあとに軽い皮肉。英語も短く平易。同じTextのペアと同じChoice/Effect/Stateを使用する。UI構造とsrc/main.tsは維持し、言語のみのメニュー、緑のログ、下部全幅一列、Safe Area、44px、typewriter、tap skip、reduced-motionを残した。

## 検証と体験評価の限界

npm test、npm run build、git diff --checkはすべて成功。Chromiumもja/enのA/B/C全6プレイとUI検証に成功。単体は3問題の観察と因果、誤操作、双方の電力解法、全ヒントと無ヒント、罰なし・段階保持、ja/en一致、無効操作、履歴コピー、restart、有限State探索による全Scene/Choice到達を確認する。

Chromiumはja/en・320×640で実ボタン操作。A：無ヒントでCLEAR。B：各問題で最終ヒントまで使用してCLEAR（順番運転）。C：扉再押下・工具で力任せ・同時再起動の結果を見て修正しCLEAR。各操作のStateを参照Gameと比較し、結果文の表示を確認する。START前・進行中・CLEAR後の言語変更でStateと履歴不変、320px横幅、全幅一列、44px、ログ領域、dropdownの配置、typewriter中の無効化、tap skip、途中からのreduced-motion、非ゼロSafe Area（上24・右16・下20・左16px）を確認。成果物は `/tmp/exit-sequence-browser/report.json` と各言語A/B/Cの画像。

自動検証は「因果の情報があり、知識不要の経路が成立し、詰まずに進める」ことの確認。実際に面白いと結論付けるには初見の人のプレイが必要。次の評価を行う：

- 最初の異常を自分の言葉で説明できるか。
- 原因をどの観察／ヒント段階で説明できたか。内部hintLevelとobservationも記録する。
- 原因発見後、最終ヒント前に対処を提案できるか。
- 誤操作後に「変わっていない原因」を理解したか。
- 成功後に「何を変えたから動いた」を説明できるか。
- 知識あり／なし双方で、自分で発見して直した感覚と所要時間を聞く。

原因画面への導線が分かりやすすぎて受動的になる可能性と、短い一段の判断に満足感があるかを重点的に観察する。ヒント利用は失敗や低評価として扱わない。
